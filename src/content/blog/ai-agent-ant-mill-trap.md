最近我重新注意到一個叫做「蟻旋」（ant mill）的現象。

行軍蟻主要依靠費洛蒙與鄰近同伴移動。這套簡單規則平常非常有效，能讓大量個體在沒有中央指揮的情況下快速協作。

但當一群螞蟻脫離主要路徑，意外形成封閉的環形軌跡時，每隻螞蟻仍然在做「正確」的事：跟著前方、沿著訊號繼續走。結果卻可能是整個蟻群不斷繞圈，直到精疲力竭。

這不是單純的「盲從」故事。更值得注意的是：

**每個個體都正確執行局部規則，整個系統卻失去了全局方向。**

這讓我想到現在快速發展的 AI agent 與 multi-agent engineering workflow。

## AI Agent 也會沿著「費洛蒙」前進

對 Agent 來說，prompt、spec、ticket、文件與前一個 Agent 的輸出，就是它所接收到的路徑訊號。

Agent 通常不會毫無理由地亂做。相反地，它很擅長根據目前上下文，產出一個看起來合理的下一步：

- Planner 根據需求拆出任務
- Researcher 根據任務整理資料
- Coder 根據規格完成實作
- Reviewer 根據規格檢查程式碼
- Fixer 根據 review comment 修正

整套流程看起來有分工、有審查，也有完整閉環。

但如果最初的需求理解就是錯的呢？

Planner 會把錯誤理解拆得很完整。Researcher 會尋找支持這個方向的資料。Coder 會忠實完成錯誤規格。Reviewer 如果也只拿同一份規格當標準，甚至可能給出「符合需求」的結論。

每一個 Agent 都完成了自己的工作，整體卻離真正的問題愈來愈遠。

這就是 AI 工作流裡的高速蟻旋。

## 多 Agent 的共識，不一定是獨立驗證

我們很容易以為，只要多放幾個 Agent，讓它們互相 review，答案就會更可靠。

但如果這些 Agent：

- 使用相同的模型
- 讀取相同的上下文
- 依賴相同的上游摘要
- 以相同的 spec 作為唯一標準

那它們形成的可能不是獨立共識，而是共享偏誤。

後面的 Agent 看到前面的產物愈完整，反而愈容易把它視為已確認事實。錯誤會經過格式化、補充與反覆引用，逐漸變得更有說服力。

所以 multi-agent 帶來的未必是多個觀點，也可能只是同一條路徑上的更多執行者。

**增加 Agent 數量可以提高產出速度，卻不會自動提高方向正確率。**

## AI 會放大流程，也會放大錯誤方向

以前人類團隊走錯方向，通常還會受到速度限制。

需求要開會、規格要整理、程式要慢慢寫、PR 要排隊 review。這些摩擦雖然讓人煩躁，有時也意外提供了重新思考的機會。

Agent 把這些摩擦大幅壓縮後，一個模糊指令可以在短時間內變成完整規格、實作、測試與文件。等人類再次介入時，錯誤方向可能已經累積成一套「看起來完成」的系統。

這也是為什麼 AI 工程的核心問題不只是：

> 我們能不能讓 Agent 做更多？

而是：

> 我們有沒有能力在它跑得很遠以前，確認它正在往對的地方走？

## 工作流需要「破圈機制」

AI agent workflow 不能只設計 happy path，還要刻意設計能夠打斷錯誤路徑的機制。

### 1. 執行前先建立方向基準

在 Agent 開始大量工作前，至少要說清楚：

- 真正要解決的問題是什麼
- 目標與非目標是什麼
- 哪些是已驗證事實，哪些只是假設
- 重要限制來自哪個原始來源
- 怎樣才算成功，怎樣代表方向錯了
- 最後由誰做決策並承擔結果

如果這些問題還沒有答案，增加 Agent 只會更快放大模糊。

### 2. 讓驗證者回到原始證據

真正的獨立驗證，不是讓 Reviewer 只看 Planner 整理過的 spec，也不是讓第二個 Agent 重讀第一個 Agent 的摘要。

驗證者應該能直接回到：

- 原始需求與使用者情境
- API contract 或正式文件
- production data、log 與可重現案例
- 法規原文或具有決策權的人
- 可執行的測試與驗收證據

否則 review 很可能只是確認大家都忠實地沿著同一條錯路前進。

### 3. 明確定義停止條件

Agent 不應只知道什麼時候完成，也要知道什麼時候必須停下來。

例如：

- 原始資料彼此矛盾
- 需求需要自行猜測關鍵商業規則
- scope 超出已授權範圍
- 涉及法規、安全、金流或不可逆操作
- 測試通過，但無法證明使用者問題真的被解決

好的 Agent 不是永遠向前跑，而是能辨識什麼時候不該繼續跑。

### 4. 依任務風險分配自治程度

不是所有工作都需要相同的人類介入。

範圍明確、可測試、可回復的任務，例如格式整理、既有 pattern 下的小型修改、測試補強與 bounded research，可以給 Agent 較高自治權。

需求模糊的 greenfield 專案、跨系統架構取捨、法規判斷、production 高風險操作，則應保留明確的人類決策關卡。

自治程度不該取決於 Agent 看起來有多聰明，而要取決於錯誤是否容易被發現與回復。

### 5. 不要只衡量產出速度

如果團隊只看完成多少 ticket、產生多少程式碼、縮短多少開發時間，很容易獎勵高速蟻旋。

更有意義的指標還包括：

- 人工介入比例
- 需求誤解率
- review 後重做比例
- production defect 與回滾次數
- Agent 產出被接受前需要多少修正
- 從發現方向錯誤到停止執行花了多久

AI 工作流的價值不是讓系統永遠忙碌，而是讓正確成果用更低成本抵達。

## 人類不是前面的那隻螞蟻

在 Agent workflow 裡，人類的價值不是逐步指揮每一個動作，也不是把 AI 當成需要全天監工的 junior engineer。

人類更重要的角色，是能暫時站到路徑之外，判斷：

- 這是我們真正要解的問題嗎？
- 現在的共識來自證據，還是來自重複引用？
- 所有 Agent 是否共享了同一個未驗證假設？
- 我們跑得更快，是因為流程更好，還是只是更快累積錯誤？

AI 讓執行愈來愈便宜，但也讓「選對方向」變得更重要。

未來成熟的 AI 工程團隊，不會只是擁有更多 Agent，而是擁有更好的方向基準、停止條件、獨立驗證與責任設計。

因為真正危險的從來不是 Agent 不工作。

而是所有 Agent 都非常努力、彼此配合、快速前進——卻沒有人發現整個系統正在繞圈。
